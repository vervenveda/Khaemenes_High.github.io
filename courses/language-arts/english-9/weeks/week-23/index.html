Unit 08 · Week 23

Technical Reading & Procedural Writing

How can a writer make a process accurate, safe, and reproducible?

Reading: Instructions, diagrams, specifications, safety notes, decision points, warnings, and troubleshooting guides.
Writing: Design a procedure for a real user, test it without rescuing the user, record failures and ambiguity, revise, retest, and preserve the evidence trail.

Weekly Targets

By the end of this week, the student can…

  • Read technical texts for purpose, prerequisites, materials, specifications, sequence, decision points, warnings, constraints, expected results, and recovery paths.
  • Distinguish a procedure from a description of what someone usually does.
  • Write observable, executable steps using precise verbs, nouns, quantities, units, locations, and conditions.
  • Use imperative mood appropriately and conditionals to represent genuine branches: if X occurs, then do Y.
  • Identify variables and constraints that can change whether a procedure succeeds.
  • Separate hazard/safety information from ordinary tips and avoid inventing safety claims.
  • Test instructions with a user while resisting the urge to explain missing information aloud.
  • Convert user hesitation, error, questions, and failure into revision evidence.
  • Write troubleshooting guidance based on observed or verified failure states rather than imaginary certainty.
  • Use accurately: procedure, specification, variable, constraint, troubleshooting, usability.
  • Complete a tested procedure, revision log, retest, and defined scored checks at 80% or higher.

Five-Day Usability Laboratory

Reverse-engineer → specify → branch → test → retest.

Day 1 · Instruction Autopsy

What Does the User Need Before Step One?

Reverse-engineer contrasting instructions, diagrams, warnings, specifications, and troubleshooting guides.

  • Identify audience, goal, prerequisites, materials/tools, starting state, sequence, expected end state, and assumptions.
  • Mark quantities, units, locations, tolerances, labels, and terms that require definition.
  • Find decision points and conditions hidden inside paragraphs.
  • Identify one instruction that depends on knowledge the writer never supplied.
  • Save an annotated technical-text map.
Day 2 · Precision Engineering

Replace “Do It Carefully” With Executable Language

Choose a safe classroom-appropriate process and create its specification before drafting steps.

  • Define the intended user and successful outcome.
  • List prerequisites, materials, constraints, variables, and observable completion criteria.
  • Replace vague verbs such as handle, fix, prepare, adjust, or set up with precise actions where possible.
  • Use exact quantities/units only when they are known and necessary; do not manufacture precision.
  • Separate mandatory requirements from optional tips.
Day 3 · Branching Language Lab

Real Procedures Are Not Always Straight Lines

Study imperative mood, conditionals, modifiers, warnings, notes, and troubleshooting branches.

  • Write concise imperative steps with one clearly identifiable action or tightly linked action set.
  • Convert hidden assumptions into explicit conditions.
  • Build at least two if/then branches for genuine alternate states where the chosen process requires them.
  • Place warnings before the action they govern when verified safety information is necessary.
  • Use all six weekly vocabulary terms accurately.
  • Complete the scored technical-language check at 80% or higher; review and retry below 80%.
Day 4 · Silent User Test

Do Not Rescue the Instructions

Give the draft to an appropriate tester. The writer observes without supplying missing directions unless safety requires intervention.

  • Record hesitation, rereading, wrong turns, skipped steps, questions, unexpected interpretations, and failure points.
  • Distinguish user error from documentation-induced error instead of blaming the tester automatically.
  • Stop any test that becomes unsafe; safety outranks the experiment.
  • Revise the document in PROSE from observed evidence.
  • Preserve the pre-test draft and observation log.
Day 5 · Retest & Troubleshooting Defense

Did the Revision Actually Fix the Failure?

Retest the revised procedure. Compare the second user's experience or a controlled repeat with the original failure record.

  • Verify whether the targeted ambiguity/failure decreased.
  • Add troubleshooting only for plausible, observed, or verified failure states.
  • Explain one revision caused directly by usability evidence.
  • Identify one remaining limitation or untested condition.
  • Preserve specification, drafts, language check, test log, revision log, retest evidence, final procedure, and reflection.

Sovereign Procedure Game

The Human Compiler

A procedure is treated like instructions executed by a human interpreter. The tester may follow what is written—not what the writer meant.

Pass 1 · Literal Run

Use a harmless classroom process. The tester follows each instruction as literally and reasonably as possible. Any point requiring the tester to guess is marked as an ambiguity token.

Pass 2 · Branch Breaker

Introduce a safe alternate starting condition: a missing optional item, different interface state, alternate orientation, or other relevant variable. Determine whether the instructions contain a valid recovery or branch.

Pass 3 · Patch & Retest

The writer patches only documented weaknesses, then retests. A successful revision must improve execution without creating unnecessary complexity elsewhere.

Eiren · Language Arts Mentor

Eiren becomes the ambiguity hunter.

Bring the specification, procedure, test log, or troubleshooting branch first. Eiren can look for missing prerequisites, vague referents, hidden conditions, impossible sequence, inconsistent terminology, and places where a user must guess.

Open Eiren
Try: “Follow only what I wrote and identify where you would have to guess.” · “Find the condition I assumed but never stated.” · “Ask what observable result proves this step succeeded.” · “Challenge troubleshooting advice that I have not observed or verified.” Eiren cannot certify physical safety, invent technical specifications, replace real user testing, write the assessed procedure, assign verified scores, or override mastery.
